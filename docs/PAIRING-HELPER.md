# Local pairing helper contract

`pairConfiguredPhone` in `src/droiddock/pairing.ts` is the process step for [issue #42](https://github.com/hooware-ai/droiddock/issues/42). The local service now exposes it only through the current browser controller's narrowly typed WebSocket messages for [issue #43](https://github.com/hooware-ai/droiddock/issues/43); the page does not yet present a pairing form. The physical phone must display **Pair device with pairing code**, and the user must explicitly request an attempt. This helper does not select a phone, change the configured permanent identity, issue `adb connect`, verify a transport, or establish that video renders. ADB itself may try to connect automatically after successful pairing.

The caller supplies the configured ADB executable, the configured permanent serial, one six-digit code, and optionally the canonical IPv4 pairing endpoint shown on the phone. Automatic endpoint selection requires exactly one configured-phone `_adb-tls-connect._tcp` advertisement and one code-pairing `adb-*` `_adb-tls-pairing._tcp` advertisement at the same address, with no listed transport for the configured serial. A `studio-*` QR pairing advertisement is contradictory for a code attempt and stops this helper. This is only a candidate association, not identity verification. An explicit manual endpoint can be used when mDNS is missing or returns no matching rows; contradictory or ambiguous mDNS evidence cannot be overridden. Hostnames, noncanonical IPv4, loopback/multicast addresses, and invalid ports are rejected. A separate connection endpoint is never used for pairing.

The helper calls only `adb devices -l`, `adb mdns services`, and one `adb pair <endpoint>`. The code goes to the pair process through stdin, never through arguments, environment variables, a file, or a URL. One attempt is active at a time; discovery and pairing have bounded output, individual command timeouts, a combined 15-second deadline, and cancellation. A caller may supply a server-side `expiresAtMs` for an earlier cutoff. This deadline cannot determine when Android itself expires a displayed code. The helper discards command output and returns only `paired`, `failed`, `expired`, or `unavailable`. `paired` requires an exit code of zero **and** ADB's explicit success line for the selected endpoint. A failed/expired pairing code may be indistinguishable from a connection failure. An `expired` or `unavailable` result after code submission can race a successful remote pairing; verify the configured phone's identity before another attempt. The helper never retries automatically.

The code is an immutable JavaScript string supplied by the caller. The helper drops its own temporary input reference after the attempt, but JavaScript and ADB cannot guarantee memory erasure. The service cancels the attempt on controller handoff, disconnect, or shutdown and discards late results. After ADB reports pairing, it uses the ordinary discovery path and checks `ro.serialno` against the configured permanent identity before returning `identity-verified`. This confirms only a reachable configured transport, **not** a rendered phone frame. `paired-unverified` means ADB reported success but that identity check did not finish successfully; the caller must not assume readiness or retry blindly. Do not log the request or raw result or expose this helper through a general command endpoint. A future browser form must clear its input on submit, cancellation, expiration, handoff, disconnect, and page closure.

The current controller may send `pairingRequest` with exactly a six-digit `code` and optional canonical IPv4 `manualEndpoint`, or `pairingCancel` with no other fields. No request ID, ADB verb, saved configuration, caller-supplied expiry, or general command is accepted. The only response is `pairingResult` with a coarse `result`: `identity-verified`, `paired-unverified`, `failed`, `expired`, `unavailable`, `busy`, or `cancelled`. Malformed messages receive a fixed input error. The bridge does not send a result to a displaced controller. Cancellation after code submission can race successful pairing, so `cancelled` is not proof that the phone rejected the code. A new Connect action cancels an in-flight attempt before normal discovery; it still requires a rendered frame before the app reports Connected. No pairing work runs in the video or normal input path.

The stdin form of `adb pair` and its success response are documented in the [Android ADB implementation](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/client/commandline.cpp) and [ADB Wi-Fi design](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md). Offline tests use synthetic ADB results; they do not prove live pairing or device compatibility.

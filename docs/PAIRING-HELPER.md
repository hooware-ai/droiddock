# Local pairing helper contract

`pairConfiguredPhone` in `src/droiddock/pairing.ts` is the process-only step for [issue #42](https://github.com/hooware-ai/droiddock/issues/42). The running DroidDock service and browser do not invoke it yet. The physical phone must display **Pair device with pairing code**, and the user must explicitly request an attempt. This helper does not select a phone, change the configured permanent identity, connect a transport, or establish that video renders.

The caller supplies the configured ADB executable, the configured permanent serial, one six-digit code, and optionally the canonical IPv4 pairing endpoint shown on the phone. Automatic endpoint selection requires exactly one configured-phone `_adb-tls-connect._tcp` advertisement and one `_adb-tls-pairing._tcp` advertisement at the same address, with no listed transport for the configured serial. This is only a candidate association, not identity verification. An explicit manual endpoint can be used when mDNS is missing or returns no matching rows; contradictory or ambiguous mDNS evidence cannot be overridden. Hostnames, noncanonical IPv4, loopback/multicast addresses, and invalid ports are rejected. A separate connection endpoint is never used for pairing.

The helper calls only `adb devices -l`, `adb mdns services`, and one `adb pair <endpoint>`. The code goes to the pair process through stdin, never through arguments, environment variables, a file, or a URL. One attempt is active at a time; discovery and pairing have bounded output, individual command timeouts, a combined 15-second deadline, and cancellation. A caller may supply a server-side `expiresAtMs` for an earlier cutoff. This deadline cannot determine when Android itself expires a displayed code. The helper discards command output and returns only `paired`, `failed`, `expired`, or `unavailable`. `paired` requires an exit code of zero **and** ADB's explicit success line for the selected endpoint. A failed/expired pairing code may be indistinguishable from a connection failure; the helper never retries automatically.

The code is an immutable JavaScript string supplied by the caller. The helper drops its own temporary input reference after the attempt, but JavaScript and ADB cannot guarantee memory erasure. Future controller integration must clear its input, cancel on handoff/disconnect, and verify the configured phone's permanent identity through normal discovery before reporting readiness. Do not log the request or raw result, expose this helper through a general command endpoint, or treat pairing as proof of a rendered phone frame.

The stdin form of `adb pair` and its success response are documented in the [Android ADB implementation](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/client/commandline.cpp) and [ADB Wi-Fi design](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md). Offline tests use synthetic ADB results; they do not prove live pairing or device compatibility.
